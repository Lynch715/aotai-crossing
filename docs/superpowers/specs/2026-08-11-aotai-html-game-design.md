# 穿越鳌太线 · 单文件 HTML 文字游戏 — 设计文档

日期：2026-08-11
素材：`docs/source/穿越鳌太线.docx`（番茄🍅的 deepseek 文游，已随仓库归档）

## 1. 背景与目标

原素材是一份给对话模型用的文字游戏指令集：24 个路线节点、12 个配角、7 类装备物资、四季风险表，外加一套回合格式规范。玩家把整份文档粘给 DeepSeek 就能玩。

现状的四个问题（用户确认全部命中）：

1. **数值会飘** — 金钱、负重、好感、物品消耗全靠模型心算，十几回合后背包里出现买过又没买的东西
2. **没有画面** — 纯文字墙，12 个配角只有名字
3. **操作麻烦** — 每局重贴长指令，手打 A/B/C/D，换设备就没存档
4. **剧情会脱轨** — 模型自创地点人物、写成文绉绉、忘记输出规定段落

目标：做一个单文件 HTML 游戏，前端接管全部数值与判定，LLM 只负责叙事，玩家接自己的 API key。

## 2. 非目标

明确不做（YAGNI）：

- **海拔剖面地图** — 24 节点可视化，看着酷但撑不起成本，v1 砍掉
- **运行时 AI 生图** — 慢、贵、风格不统一，还要玩家再配一个绘图 key
- **多人 / 联机 / 排行榜**
- **后端服务** — 全程纯前端，key 不经过任何第三方
- **移动端专门适配** — 双栏布局优先桌面，手机可用即可

## 3. 关键决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **判定发生在调用 LLM 之前**，前端算完把既成事实告诉 LLM | 数值零漂移的根；LLM 永远碰不到 state |
| D2 | LLM 生成选项时必须**申报门槛与代价** | 让前端有据可判，同时选项门槛可对玩家可见 |
| D3 | 交付**单个 .html**，开发时多文件 + 构建合并 | 分发简单；同时避免 5000 行单文件难以维护 |
| D4 | 布局：**双栏仪表盘打底 + 立绘舞台** | 门槛可见治"数值飘"与"莫名失败"；立绘值得真正的画面位置 |
| D5 | 原生 UI 只做**商店 / 捏人 / 抽卡** | 这三块是表格与随机，交给 LLM 是灾难 |
| D6 | **混合协议**：正文用文档原格式标记分段，尾部追加 `<<<STATE>>>` JSON | 正文格式是模型最熟的那个，几乎不崩；结算 JSON 短小可靠、可单独重试；流式打字机天然顺滑 |
| D7 | **结构化旅程档案**代替全量历史 | 上下文恒定，第 100 回合和第 3 回合一样便宜 |
| D8 | 新增**体力**作为核心资源（文档没有） | 重装徒步的核心张力，串联负重、物资、天气、海拔 |
| D9 | **扩充可选物资**，让 30kg 上限成为真约束 | 按文档原表满配只有 13–16kg，负重条形同虚设 |
| D10 | 硬门槛 + **边缘掷骰** | 纯硬门槛让游戏变查表；差距过大的选项置灰而非浪费回合 |
| D11 | 立绘**程序化占位 + 目录约定替换** | 没有美术资源也能立刻玩；有图了零改代码升级 |

## 4. 架构

两个区，边界就是"谁能改 state"。

### 权威区 · 前端引擎（唯一真相来源）

| 模块 | 职责 |
|---|---|
| `data` | 静态数据：`ROUTE` 24 节点、`NPCS` 10+2 人、`GEAR` 装备表、`EXTRA_GEAR` 扩充物资、`SEASONS` 四季风险 |
| `state` | 权威状态对象。纯数据，导出即完整存档 |
| `rules` | 门槛比对、掷骰、消耗结算、位置推进、结局判定 |
| `journal` | 旅程档案：走过的节点、关键事件、未收伏笔、人物状态；含超限压缩 |

### 提议区 · LLM（只写字，输出一律先过校验）

产出三类：正文（标题 + 300 字剧情 + 鳌太万象 ×4）、选项（A/B/C/D 文案 + 申报门槛 + 申报代价）、结算提议（好感增减、记忆条目、伏笔变动、天气与去向建议）。

### 支撑模块

| 模块 | 职责 |
|---|---|
| `llm/client` | OpenAI 兼容 fetch、SSE 流式、重试与退避 |
| `llm/prompt` | 组装 system（常驻）与每回合 user message |
| `llm/parser` | 混合协议解析：标记分段 + 尾部 JSON |
| `ui/setup` | 捏人表单 + 队友抽卡 |
| `ui/shop` | 物资采购 |
| `ui/game` | 主界面：左栏面板 + 立绘舞台 + 剧情流 + 选项 |
| `ui/settings` | API 配置 |
| `ui/portraits` | 立绘加载与占位生成 |
| `persist` | localStorage 存档、导出/导入、版本迁移 |

### 一个回合的流转

```
1. 玩家点选项 C「你打头阵，用绳子做保护」        [前端]
2. rules 比对上回申报的门槛：经验 38 < 60 → 判定失败   [前端 · LLM 尚未参与]
3. rules 先行结算硬资源：中→晚、体力 −9、干粮 −2         [前端]
4. prompt 组装 system(常驻) + user(档案 + 最近3回合 + 既成事实 + 状态快照)
5. LLM 流式返回；正文边流边上屏，遇 <<<STATE>>> 转静默收集   [LLM ↔ 前端]
6. 校验尾段 JSON：好感夹 0–100、物品须存在于 GEAR/EXTRA_GEAR、
   去向须为 ROUTE 合法相邻节点、负重不得超上限          [前端 · 越权提议驳回并记 warn]
7. 原子应用 → journal 追加 → localStorage 落盘 → 面板刷新   [前端]
```

## 5. 数据模型

```js
state = {
  meta:    { 版本, 季节, 随机种子 },     // 种子固定 → 同一存档判定可复现
  phase:   '准备' | '徒步' | '结局',
  clock:   { day: 4, slot: '早' | '中' | '晚' },   // 文档「按早中晚推进」
  place:   { nodeId, 海拔 },
  weather: { 状态, 等级 },
  pc:      { 名字, 职业, 年龄, 性别, 性格, 外貌, 技能[], 户外经验, 体力, 伤病[] },
  money:   4320,
  pack:    [ { gearId, 数量, 单重, 余量 } ],
  carry:   { 当前, 上限: 30 },
  party:   [ { npcId, 好感, 状态, 在队 } ],
  flags:   { 已求救, 已下撤, 触发过的事件id[] }
}
```

初始金钱 1 万（文档）。负重上限 30kg（文档）。

## 6. 判定与结算规则

### 判定

LLM 为每个选项申报 `require`（门槛）与 `cost`（代价）。前端拿权威 state 比对：

| 差距 d | 结果 | UI |
|---|---|---|
| d ≤ 0（达标） | 成功 | 正常可点 |
| 1 ≤ d ≤ 10 | 掷骰，成功率 `P = 0.9 − 0.07 × (d − 1)`（d=1 → 90%，d=10 → 27%） | 标黄，显示取整后的百分比 |
| d > 10 | 直接失败 | 置灰不可点，"差 22 点经验" |

掷骰用 `meta.随机种子` 驱动的可复现 PRNG，同一存档重放结果一致。多条门槛同时不满足时取**最大差距**判定。

**对文档的偏离**：文档原文是"数值不够则下回合失败"（纯硬门槛）。加入中间掷骰档是为了保留赌一把的余地；把差距过大的选项置灰而非让玩家白白浪费一回合，是因为原规则玩起来挫败感过强。

### 防 LLM 乱报价

| 选项类型 | 好感门槛上限 | 经验门槛区间 |
|---|---|---|
| 社交（聊天 / 示好 / 请教） | ≤85 | 0–30 |
| 徒步技术（横切 / 攀爬 / 探路） | ≤60 | 20–75 |
| 高危（夜路 / 独行 / 强推） | ≤70 | 40–90 |

超范围夹取，console warn，不打断流程。

### 前端硬扣的消耗（LLM 完全不参与）

消耗：

- 每时段体力 −6；负重每超 1kg 再 ×1.04（以 15kg 为基准线，`超出 = max(0, 当前负重 − 15)`）；海拔 >3400 且未适应额外 −2
- 每天主粮 −2；热食一次气罐 −8%；水仅在有水源的节点可补

回复：

| 行为 | 体力 | 前置 |
|---|---|---|
| 一个时段原地休整 | +8 | 消耗一个时段 |
| 进食（热食） | +6 | 消耗气罐与冻干餐 |
| 进食（路餐冷食） | +3 | 消耗路餐 |
| 夜间睡眠 | +25 | 需帐篷 + 睡袋；无营地或恶劣天气减半 |

体力低于 20 时门槛判定额外 +10 惩罚差距（累到极限会走向"失败遇险"结局）。

### 好感

0–100，前端夹取。分级：`0-19 冷淡 / 20-39 面熟 / 40-59 搭伙 / 60-69 信任 / 70-89 爱慕 / 90-99 深爱 / 100 至死不渝`（70 与 100 两档为文档明写）。

LLM 单回合最多申报 ±5；救命级事件可申报 ±15，但必须带 flag 标记。

初始好感由**捏人性格与 NPC 性格的匹配度**计算，不是固定值：

给每个 NPC 与每个可选性格标签打上若干性格轴（如 内敛↔外向、谨慎↔冒进、独行↔合群、务实↔理想）。初始好感 = `25 + Σ(轴匹配 +4 / 轴冲突 −4)`，夹取到 10–45。举例：捏人选"话不多、认死理"配陈岩"沉稳寡言"→ 偏高；配韩梅"强势控制欲"→ 偏低。

### 三种结局（文档定死）

- **失败遇险** — 体力归零 / 严重伤病未处理 / 失温判定连续失败
- **被救援** — 主动求救（卫星电话或信标），或触发他人救援
- **成功穿越** — 抵达下板寺，罚款 5000 元

## 7. 装备与扩充物资

文档原表 7 类 21 项照搬，含经济/主流/轻量三档价格与重量。

**问题**：按中档满配 14.1kg / ¥14,375（超出 1 万预算），但总重仅 14.1kg，30kg 上限走不到一半。负重不是约束，钱才是。

**解法**：新增一批"带不带都行"的可选物资，每样都有真实作用但压秤，让负重与金钱同时成为约束。

**合计 16.05kg / ¥7,630。** 与原表中档（14.1kg / ¥14,375）相加 **30.15kg / ¥22,005**，对上 30kg 与 ¥10,000 两条线：

- **钱是硬约束** — 只买得起约 45%，必须放弃一批东西
- **重量是软约束但会咬人** — 水和额外口粮**便宜且压秤**（3L 水 3kg 只要 ¥120，水本身免费），追求容错的玩家会先撞上 30kg
- 两条线互相拉扯：省钱的路线是多带便宜的水和粮，那就撞重量；轻装的路线是买贵的轻量装备，那就撞预算

具体数值以实测手感为准，首轮实现后按体感调档。

## 8. LLM 契约

### system prompt（常驻不变，命中各家 prompt cache）

四部分：

1. **总则** — 所有地点、人物、装备只能取自给定数据，不得自创
2. **静态数据** — 24 节点 + 12 人 + 装备表 + 四季表，压缩成紧凑 JSON
3. **文风约束**（抄文档原话）— 300 字左右、口语化、禁文绉绉、禁心理描写、禁比喻隐喻意象、禁上帝视角、减少环境器物描写、不得出现数值、不得未卜先知
4. **输出协议规范 + 一个完整范例**

### 每回合 user message

```
【旅程档案】
  已过节点：塘口村 → 火烧坡 → 2900营地 → 水窝子 → 麦秸岭
  关键事件：D2夜 王大鹏膝盖旧伤复发，你分了他布洛芬
           D3午 水窝子遇独行的沈冰，未同行
  未收伏笔：石缝里那截褪色路标带还没人去查
           对讲机里断续的呼叫，未确认来源
  人物：陈岩 正常｜林晓雅 轻度高反｜王大鹏 已下撤

【最近 3 回合原文】…

【本回合既成事实】
  玩家选 C，判定失败（经验不足）
  已结算：中→晚｜体力 50→41｜干粮 −2｜位置不变

【当前状态快照】
  第4天 晚｜麦秸岭 3500m｜大风6级｜负重 26.8kg｜现金 ¥4,320
```

**档案中不写数字好感**，只写"正常 / 轻度高反"这类状态。文档禁止 LLM 开天眼，给它精确数值它就会在对话里漏出来。数字只留在前端。

### 输出格式

沿用文档原格式：`[剧情标题]` / `[剧情]` / `[鳌太万象]`（4 条）/ `[下回选项]`（A-D），末尾追加：

```
<<<STATE>>>
{ "好感":[{"npc":"林晓雅","delta":3,"因":"你退后让她先过"}],
  "记忆":["D4傍晚 麦秸岭 你逞强打头阵失败，陈岩当众制止"],
  "伏笔":{"新增":[],"已收":["石缝路标带"]},
  "天气建议":"转北风，夜间可能降雪",
  "去向建议":"水窝子营地",
  "选项":[{"id":"A","类型":"社交","require":{"好感":{"林晓雅":40}},"cost":{"体力":8}}, …] }
```

## 9. 错误处理与降级

**铁律：任何 LLM 故障都不能损坏 state。** 结算是原子的——全套校验通过才一次性应用；每回合开始前打快照，出错回滚。

| 故障 | 处理 |
|---|---|
| STATE 缺失或 JSON 解析失败 | 正文已上屏保留，单独补发"只输出 STATE"请求，重试 2 次 |
| 补救仍失败 | 正文保留，本回合不结算，选项换成前端兜底四项（继续前进／原地休整／找人搭话／清点装备），游戏不卡死 |
| 门槛越界 | 夹取到该类型区间，console warn，不打断 |
| 引用不存在的人/物/地点 | 丢弃该条提议，其余照常应用 |
| 网络错误 / 429 / 超时 | 指数退避重试 3 次；仍失败则不消费玩家选择，显示重试按钮 |
| 流中途断开 | 已上屏正文保留，标记"未结算"，提供续写按钮 |
| CORS 被拦 | 与 key 错误明确区分，提示换厂商或起本地代理 |
| 上下文超限 | 档案压缩（留最近 20 条事件 + 全部未收伏笔），最近回合原文由 3 降 1 |

**降级取舍**：选择"正文保留、不结算、给兜底选项"而非"报错卡住"。代价是该回合好感变化与记忆丢失、剧情连续性有小坑；换来的是游戏永不卡死。

## 10. 游戏流程与界面

### 三阶段（文档定义）

```
准备阶段（全原生 UI，一次 LLM 都不调）
  API 配置 → 捏人 → 季节掷定（随机，公示）→ 抽卡（即文档的「论坛邀约驴友」）→ 商店采购
       ↓
徒步阶段（每回合一次 LLM 调用，早/中/晚 三段推进，无限至结局）
  第 1 天早晨 从塘口村或苗圃进山起算
       ↓
结局页（三种之一 + 旅程回顾：走过的节点、关键事件、最终好感）
```

文档把"论坛邀约驴友、采购装备"写成前期准备 3 天。本设计**把这 3 天折叠进原生 UI**，不占用徒步回合——因为这三件事全是表格与随机，走 LLM 回合既慢又容易出错（D5）。徒步阶段的第 1 天早晨从进山起算。

**季节在捏人之后、抽卡与采购之前掷定并公示**——玩家必须知道自己面对的是哪一季才能针对性备货（冰爪之于冬季、防蚊液之于夏季）。这也是文档"每个季节危险和准备不同"的落点。

### 主界面（双栏仪表盘 + 立绘舞台）

- **左栏常驻**：角色头像与基本信息、负重条（接近上限变黄）、体力条、现金、同行者列表（小头像 + 好感条）、背包摘要（含每日消耗提示与余量告警）
- **右栏**：顶部状态条（天数/时段/地点/海拔/天气）→ 立绘舞台（**仅 NPC**，说话人高亮，非说话人降透明度，好感变化飘字）→ 剧情标题与正文（打字机流式）→ 鳌太万象 4 条 → 选项区
- **选项明码标价**：达标显 ✓、勉强标黄写概率、不达标置灰写差多少

### 准备阶段三屏

- **捏人** — 名字/职业/年龄/性别/性格/外貌/技能（选 3）表单，户外经验由职业+技能+年龄推算并可手调 ±10，带"随机一个"
- **抽卡** — 从 10 人随机 2 人，卡片展示技能/性格/初始状态（如"王大鹏 · 膝盖旧伤复发"），限重抽 1 次
- **商店** — 7 类 20+ 项 + 扩充物资；三档价格行内切换；实时总价/总重双进度条；按季节生成的警告与缺件清单；"一键推荐配置"

## 11. 立绘系统

- **占位**：以 `npcId` 做确定性哈希 → 生成剪影轮廓与配色。每个人长得不同，每次打开都一样
- **替换**：启动时探测 `assets/portraits/{npcId}.png`，有则用，无则回落占位
- **状态层（可选）**：`{npcId}_hurt.png` 等，缺失回落默认
- **规格**：512×768、3:4 半身、透明底 PNG
- **主角不上立绘舞台**：文档全程第一人称，舞台上只出现 NPC。理由与 galgame 的惯例一致——真让主角站上画面，"我就是主角"的代入感反而破了。主角只在左栏有一个 48px 小头像，按性别 + 捏人配色种子生成占位；想换可自行放 `assets/portraits/pc.png`。这也顺带解掉了"外貌由玩家自填、无法预生成立绘"的死结
- **交付附带**：**12 份 NPC 生图 prompt**（10 随机配角 + 踏雪、猛蛇过江，按文档的年龄/职业/性格/状态撰写）；一个把 assets 转 base64 内联的烘焙脚本，产出真·单文件

## 12. 存档与配置

- 每回合结算后自动写 localStorage；3 个手动槽 + 1 个自动槽
- 导出 / 导入 JSON 文件，用于换设备
- 存档带版本号，加载时走迁移
- **API 配置**：OpenAI 兼容三件套（baseURL + key + model），预设 DeepSeek／硅基流动／Kimi／智谱／OpenRouter／自定义，带"测试连接"；温度与 max tokens 可调
- key 只存本地 localStorage，界面明示不经过任何第三方服务器

## 13. 代码组织、构建与测试

- **开发**：`src/` 按模块分文件（data / state / rules / journal / llm / ui / persist）
- **构建**：`node build.mjs` 合并成单个《穿越鳌太线.html》交付
- **单测**：`node --test` 覆盖三块纯逻辑
  - `rules` — 门槛比对、掷骰边界、体力/负重/消耗算式、三种结局触发
  - `parser` — **重点喂畸形输入**：STATE 缺失、JSON 截断、中文引号、整段被 ` ```json ` 包裹、正文中恰好出现 `<<<STATE>>>` 字样
  - `journal` — 超限压缩保留哪些、丢哪些
- **LLM 客户端与 UI**：不写自动化测试，用录制的真实响应做 fixture 回放 + 手动验证

## 14. 对原文档的偏离与扩展

| 项 | 文档原样 | 本设计 | 理由 |
|---|---|---|---|
| 体力 | 无此属性 | 新增为核心资源 | 重装徒步的核心张力所在 |
| 判定 | 纯硬门槛，不够则失败 | 硬门槛 + 边缘掷骰，差距过大置灰 | 保留赌一把余地；避免白白浪费回合 |
| 装备 | 7 类 20 项 | 加一批可选物资 | 原表满配仅 13–16kg，30kg 上限失效 |
| 数值可见性 | 剧情中禁止出现数值 | 剧情仍禁止；UI 面板与选项门槛可见 | 约束管的是 LLM 正文，不是界面 |
| 好感变化幅度 | 未规定 | 单回合 ±5，特殊事件 ±15 | 防止暴涨 |
| 前期准备 3 天 | 作为 3 个游戏日推进 | 折叠进原生 UI，不占徒步回合 | 表格与随机走 LLM 既慢又易错 |

## 15. 风险

| 风险 | 缓解 |
|---|---|
| LLM 申报的门槛不合理，破坏难度曲线 | 按类型夹取 + 记 warn；实测后调区间 |
| 判定先行降低 LLM 叙事自由度 | 既成事实只给结果不给理由，留出解释空间 |
| 各家模型对协议遵守度不一 | 协议贴近文档原格式；提供 fixture 回放验证新厂商 |
| CORS 阻断部分厂商 | 预设只收录已验证可浏览器直连的；文档说明本地代理方案 |
| 单文件体积随立绘 base64 膨胀 | 烘焙为可选步骤，默认走 assets 目录 |
| 长局叙事重复 | 档案含"未收伏笔"，提示 LLM 优先收线 |
